We've built design systems for ourselves and for clients. We've also inherited design systems that were abandoned, inconsistent, or so rigid they slowed teams down instead of speeding them up. Here's what separates the ones that last.

## Start with Tokens, Not Components

A design token is the atomic unit of your design system — a named design decision that can be referenced everywhere. Before you build a single button, you need a token layer:

```
── Primitives (raw values)
│   ├── color.blue.500: #3B82F6
│   ├── space.4: 16px
│   └── radius.lg: 12px
│
└── Semantic tokens (intent-based references)
    ├── color.action.primary: {color.blue.500}
    ├── space.component.padding: {space.4}
    └── radius.card: {radius.lg}
```

**Why two layers?** Primitives are your palette — they never appear directly in components. Semantic tokens map intent to primitives and are what components actually consume. When you rebrand or add a dark mode, you change the semantic layer only. Components stay untouched.

In Figma, these become Variables. In code, they become CSS custom properties. They're the same thing — and keeping them in sync is where most systems fail.

## Component API Design is Product Design

Every component you ship is an API. Unlike a database schema, changing a component API after adoption means coordinating updates across every product that uses it. Get the API right once.

The principles we follow:

**Composition over configuration.** A `<Card>` component shouldn't have 40 props to handle every layout variant. It should have slots — `<Card.Header>`, `<Card.Body>`, `<Card.Footer>` — that let consumers compose what they need.

```tsx
// ❌ Prop soup — impossible to extend without breaking changes
<Card
  title="Project Alpha"
  subtitle="Web App"
  showBadge
  badgeColor="green"
  badgeText="Active"
  showFooter
  footerCta="View"
/>

// ✅ Composable — consumers own the structure
<Card>
  <Card.Header>
    <h3>Project Alpha</h3>
    <Badge color="green">Active</Badge>
  </Card.Header>
  <Card.Body>Web App</Card.Body>
  <Card.Footer>
    <Button size="sm">View</Button>
  </Card.Footer>
</Card>
```

**Controlled vs uncontrolled.** Offer both. Uncontrolled for simple cases (internal state), controlled for complex ones (external state management). Radix UI does this well — learn from it.

**Variants, not custom styles.** Give components a `variant` prop with defined options. Avoid `className` overrides as a primary API — they create invisible dependencies and make refactors unsafe.

## Storybook Is Your Contract

Every component should have stories that document its API contract, not just show what it looks like. Stories are executable specifications:

```tsx
export const Default: Story = {
  args: { label: "Button", variant: "primary", disabled: false },
};

export const Loading: Story = {
  args: { label: "Saving...", variant: "primary", loading: true },
};

export const Disabled: Story = {
  args: { label: "Unavailable", variant: "primary", disabled: true },
};
```

Run Chromatic on every PR to catch visual regressions automatically. A screenshot diff is worth a thousand words of code review.

## Accessibility Is Non-Negotiable

Build it in from the start. Adding WCAG compliance to a mature component library is like adding tests after the fact — painful, incomplete, and never quite right.

What "accessible by default" means in practice:

- Every interactive element has a visible focus ring
- All colour pairs in your token set pass 4.5:1 contrast (AA)
- Icons have `aria-label` or are `aria-hidden` when decorative
- Form inputs are always associated with a `<label>`
- Modals trap focus and restore it on close
- Keyboard navigation works everywhere a mouse works

We use `axe-core` integrated into Storybook to catch issues in CI before they reach production.

## The Governance Problem

The technical work is the easy part. The hard part is keeping the system alive.

Design systems fail when:
- Engineers bypass them under deadline pressure ("I'll just do it inline for now")
- Designers add components in Figma that never make it to code
- No one owns it, so no one maintains it

What works:
- **A dedicated owner** (doesn't have to be full-time, but must be accountable)
- **A contribution model** — clear process for teams to propose, review, and merge additions
- **Versioning and changelogs** — treat it like an open-source library
- **Regular audits** — quarterly sweeps to remove deprecated patterns and consolidate drift

The best design systems we've worked with had one thing in common: someone who treated it as a product, not a project. Projects end. Products evolve.

## Our Starter Stack

When we build a design system from scratch, this is our default stack:

- **Figma** — source of truth for design tokens and component specs
- **Radix UI** — unstyled, accessible primitives (handles all the hard ARIA work)
- **Tailwind CSS** — utility layer for styling
- **Class Variance Authority (CVA)** — type-safe variant management
- **Storybook** — development environment and living docs
- **Chromatic** — visual regression testing
- **Changesets** — versioning and changelog automation

This stack ships fast and scales further than you'd expect for a startup budget.

The App Router changed everything. After shipping several production applications with it at Xpersive Labs, we've built up a clear picture of where it shines, where it still has rough edges, and what patterns make teams fast.

## The Mental Model Shift

The most important thing to internalise is the Server/Client Component boundary. In the pages router, _everything_ was a client component. In the App Router, **components are server by default** — they run on the server, have direct access to databases, filesystems, and secrets, and send only HTML to the browser.

The `"use client"` directive opts a subtree back into the traditional React model. The key insight is this isn't a per-page decision — it's a **per-component** decision, and you want to push it as far down the tree as possible.

```tsx
// ✅ Server Component — runs on server, no bundle cost
async function ProductList() {
  const products = await db.product.findMany();
  return <ul>{products.map(p => <ProductCard key={p.id} product={p} />)}</ul>;
}

// ✅ Client Component — only the interactive leaf
"use client";
function AddToCartButton({ productId }: { productId: string }) {
  const [pending, startTransition] = useTransition();
  return (
    <button onClick={() => startTransition(() => addToCart(productId))}>
      {pending ? "Adding..." : "Add to Cart"}
    </button>
  );
}
```

## Data Fetching Done Right

Forget `getServerSideProps`. In the App Router, you fetch data directly inside async Server Components:

```tsx
async function DashboardPage() {
  // These run in parallel automatically via Promise.all, or sequentially if dependent
  const [user, stats] = await Promise.all([getUser(), getStats()]);
  return <Dashboard user={user} stats={stats} />;
}
```

**Deduplication is built in.** If multiple components call the same `fetch()` URL with the same options within a single render pass, Next.js automatically deduplicates the requests. No more prop drilling data down or pulling everything into a top-level component.

## Layouts and Loading UI

Nested layouts are the killer feature most teams underuse. Every segment can have its own `layout.tsx`, `loading.tsx`, and `error.tsx`. Combine that with React Suspense and you get per-segment loading states with zero boilerplate:

```
app/
├── layout.tsx          # Shell: nav, footer — persists across all routes
├── dashboard/
│   ├── layout.tsx      # Sidebar — persists within /dashboard/*
│   ├── loading.tsx     # Skeleton shown while page fetches
│   └── page.tsx        # Async server component
```

The `loading.tsx` file wraps the page in a `<Suspense>` boundary automatically. When the page's async work resolves, React streams the real content in — no full-page spinner needed.

## Route Handlers vs Server Actions

Two ways to handle mutations and API needs:

**Route Handlers** (`app/api/*/route.ts`) are for external integrations — webhooks, mobile clients, third-party callbacks. They're standard `Request`/`Response` based.

**Server Actions** are for form submissions and mutations from your own UI. They're regular async functions marked `"use server"` and called directly from components. No API route needed:

```tsx
// actions.ts
"use server";
export async function createPost(formData: FormData) {
  const title = formData.get("title") as string;
  await db.post.create({ data: { title, userId: await getUserId() } });
  revalidatePath("/blog");
}

// page.tsx
<form action={createPost}>
  <input name="title" />
  <button type="submit">Publish</button>
</form>
```

## Pitfalls We've Hit

**Context doesn't cross the Server/Client boundary.** You can't create a context in a server component and consume it in a client component. Client-side state needs to live entirely in the client tree.

**Cookies and headers are async in Next.js 15+.** `cookies()` and `headers()` now return Promises — `await cookies()`. If you're seeing type errors here, this is why.

**`"use client"` doesn't mean "browser only."** Client components still SSR on the first load. `typeof window === 'undefined'` checks still matter for browser-only APIs.

## What We Ship on Every Project

- **`next/font`** for zero-layout-shift font loading
- **`next/image`** with explicit `width`/`height` to avoid CLS
- **Parallel Route segments** for dashboard-style layouts with independent loading states
- **Intercepting routes** for modals that have their own shareable URL

The App Router is mature now. The patterns above will get you to production confidently.
